# 작업 절차와 검증

## 시작할 때

1. `git status --short`로 사용자 변경을 확인한다. 무시된 로컬 파일도 검증에 영향을 줄 수 있으므로 테스트 존재 여부를 별도로 확인한다.
2. [구조](architecture.md), [컨벤션](coding-conventions.md), [현재 상태](current-state.md)를 읽는다.
3. 대상 기능의 `__index.ts`, `__model.ts`, 핸들러와 헬퍼, 기존 README를 함께 읽는다. 가장 가까운 구현을 기준으로 삼는다.
4. 기존 API 계약과 변경할 파일·이유·검증 범위를 정한다. 요청이 기능 추가라면 관련 없는 구조 재설계를 섞지 않는다.
5. DB, 인증, 파일, mix 등 다른 경로에서 같은 함수를 호출하는지 검색한다.

## 기능 추가 순서

기존 기능 확장은 해당 폴더 안에서 요청 모델 → 개별 핸들러/필요한 헬퍼 → 라우트 등록 순으로 구성한다. 새로운 최상위 기능이면 `routes/index.ts` export와 `main.ts`의 `app.use()`를 모두 추가한다. 필요 없는 `__helper.ts`나 빈 클래스는 만들지 않는다.

스키마에는 외부 입력의 타입·범위를 정의한다. 핸들러는 DB에 필요한 검증과 처리를 맡고, 라우트는 인증과 응답을 연결한다. 특수 HTTP 기능이 필요하지 않다면 `ctx` 전체 대신 `{ body, query, token, service }` 중 필요한 값만 전달한다.

인증 변경은 [변경 지도](auth-and-providers.md), 저장 구조 변경은 [스키마 변경 지침](data-and-storage.md)을 따른다. 문서·기능 README도 구현과 같은 변경에 포함한다.

## 검증 명령

프로젝트 루트에서 실행한다. 설치가 필요하면 `bun install --frozen-lockfile`을 사용하고 의도하지 않은 lockfile 변경을 확인한다. 여기 적힌 명령이 모두 현재 통과한다는 의미는 아니다.

```sh
# 로컬에 설치된 컴파일러: 네트워크 다운로드 없이 검사
./node_modules/.bin/tsc --noEmit

# 전체 테스트 / 특정 파일
bun test
bun test tests/<feature>.test.ts

# 번들 빌드: dist를 재생성하므로 필요할 때 실행
bun run build

# 변경 확인
git diff --check
git diff --stat
git status --short
```

`package.json`의 test 스크립트도 `bun test`다. 타입 검사 전용 script는 없다. Bun 번들링은 TypeScript 타입 검사와 별개다. 빌드 스크립트는 `Bun.build()` 결과의 success/logs를 명시적으로 검사하지 않으므로 완료 문구만으로 검증을 대체하지 않는다.

`bun run dev:preview`는 실제 설정으로 서버를 실행하고 설치 상태를 요구한다. 테스트할 때는 임시 `PATH_DATA`와 테스트용 비밀 값으로 격리한다. `install`, `uninstall`, `reset-password`, 캐시 `--execute`를 현재 데이터에 검증 목적으로 실행하지 않는다.

## 변경별 확인 범위

| 변경 | 확인할 동작 |
| --- | --- |
| 문서만 | 파일 경로·링크, 소스와 설명 일치, diff 공백 오류 |
| CRUD | 정상/잘못된 입력, 미존재 데이터, 중복, PATCH 미지정과 빈 값, 권한 |
| 인증 | 정상·실패 로그인, 만료·폐기·갱신, 공개용 토큰과 관리 권한, 기존 provider 회귀 |
| 삭제·관계 | 연결 데이터 및 파일 정리, 실패 시 rollback 범위 |
| 파일/캐시 | 캐시 적중·미스·손상, MIME/charset, 공개 상태 전환 후 접근 |
| mix 대상 | 직접 API와 mix 양쪽 입력·권한·실패 처리 |
| 스키마 | 새 임시 DB와 기존 구조의 임시 DB, 데이터 보존·전환 재실행 |

테스트는 구현을 그대로 복제하는 대신 외부에서 관찰할 계약과 실패 조건을 확인한다. 로컬 실제 DB를 사용하지 않는다. 싱글턴 `db`나 환경변수를 바꾸는 테스트라면 연결 종료, 원래 값 복원, 임시 파일 정리를 보장한다.

현재 `.gitignore`가 `tests/` 전체를 무시한다. 새 테스트 작성 시 파일이 로컬에만 남지 않도록 추적 정책을 함께 검토한다. 무시된 기존 테스트를 임의로 삭제하거나 의존성을 복원하지 않는다. 잔여 파일로 인한 기존 실패는 변경으로 생긴 실패와 구분해 보고한다.

## 완료 전에 직접 확인할 것

- 파일명·중괄호·import 배치·export가 컨벤션과 맞는가?
- 등록 파일에 업무 로직이 쌓이거나 하나의 클래스에 여러 책임이 합쳐지지 않았는가?
- 요청 스키마와 파생 타입이 연결되어 있는가?
- 기존 URL/메서드/응답/상태 코드/토큰 의미를 보존했는가?
- 외부 값의 SQL 바인딩, PATCH의 미지정 값, DB/파일 부수효과를 확인했는가?
- 필요한 검증을 실제 실행했고 기존 실패와 새 실패를 구분했는가?
- 생성한 파일이 Git에서 보이는가? 비밀 값이나 실제 데이터를 추가하지 않았는가?
- 문서 변경과 미검증 범위까지 결과에 기록했는가?

완료 보고에는 변경 내용·이유, 실행한 검증과 결과, 남은 한계를 간단히 적는다. 포매터·테스트가 없는 영역을 통과했다고 표현하지 않는다.
